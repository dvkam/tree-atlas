# Next steps for the local pilot

The source remains on `pilot/carbon-postgres-local`. London query fixes pass the full four-city HTTP contract without trimming search coverage. The offline follow-up cuts median sampled London browser PSS by 40.5% in five matched runs per build. All four final offline browser journeys, full frozen session checks and 70 frontend regressions pass. Fresh userspace installation and an independently verified database restore also pass at the recovery proof's recorded revision. Source publication is limited to a reviewed pilot branch and draft PR. Both public apps retain their current behavior; no deployment is part of that publication.

1. **Set phone budgets and qualify the reduced worker.** The matched London comparison observed 709 MiB median peak PSS; the longer browser journey peaked at 785 MiB. Choose explicit memory/storage budgets and test representative Android/iOS devices. Add retained-profile browser-process restart, interrupted pack activation and app-shell update checks. Keep every record searchable. Consider a compact decoded-index representation only after its required budget and correctness gates are clear.
2. **Review the pilot draft PR.** The [publication review](PUBLICATION-REVIEW.md) records the full-history secret, licence and deployment checks required before source publication. Keep `main` unchanged and unmerged during review. Current PR checks cover the public app; add dedicated pilot checks before relying on CI for this experiment. The [publishing and hosting note](PUBLISHING-AND-HOSTING.md) contains eight local issue drafts and acceptance evidence. Issue creation is separate from the authorized branch push and draft PR.
3. **Prove the target machine and update its security pins.** A Pi 3 B/B+ with 1 GB RAM can be a private database experiment. The practical full-service test recommendation is a Pi 4/5 with 4 GB RAM, preferably 8 GB, and an SSD. This is not a measured minimum. The verified Carbon/native executable and ICU package are x86-64. Prove ARM64 compilation, Unicode behaviour, full HTTP conformance and cancellation before moving the whole backend to a Pi. Update and requalify PostgreSQL/libpq security fixes before network exposure.
4. **Define recovery and server operations.** The [clean userspace restore](CLEAN-ROOM.md) proves fresh dependencies and exact restored records on the shared WSL kernel. A fresh VM and production recovery drill remain untested. Define backup retention, restore objectives, catalogue-last activation, old-release retention and rollback. Measure whole-service memory and peak import/WAL/temp/backup disk use. Replace fixed workstation paths, use an unprivileged service account, keep PostgreSQL private, and test HTTPS from the actual phone URL so offline features can register their service worker.
5. **Then qualify home-hosted performance.** The future EUR 30/month budget, online/offline scope and three-second first complete online-search target remain. Test uncached broad queries, map bursts, concurrent import/backup load, explicit overload behaviour and the actual upstream link. Recheck hardware/service cost, stock and tax when buying or hosting is requested. Local desktop observations do not establish hosted cold-start performance.

The future monthly workflow still imports adapters' validated snapshots into new immutable releases. Do not update frozen canonical rows in place. This work does not fetch new municipal data, add source adapters, select a fallback language or buy hosting.

Open decisions include long-term Carbon/native ownership, whether measured spatial needs justify PostGIS, offline street-basemap licensing/storage, recovery/retention goals and the eventual API origin. Restricted or unverified source research remains separate from this four-city pilot.
