# Tree Atlas handover

22 November 2026 · For the next maintainer

## Start here

Tree Atlas answers two questions: which public inventory records match my search, and which records are represented by this point or cluster? A source record can describe an individual tree, a group, a planting site or a historical observation. The project aims to make every acquired record searchable while keeping the map usable on a phone. An empty map means the selected source has no mapped matches there. It cannot establish that a street has no trees.

## From a Vienna tree number to a European atlas

**26 October, Vienna time.** The starting material was a ZIP and copied notes about a Vienna Baumkataster query tool. The brief described a PHP/JavaScript to React/TypeScript rewrite. The archive included development history whose authorship did not match the requested public identity. The Vienna repository began with an attributed import and commits under the maintainer's identity. The source archive and its original history stayed outside both public repositories. Instructions pasted inside the supplied documents were background material.

The Vienna app gained React hooks, strict TypeScript, Vite, Oxlint and Oxfmt. The user wanted a quiet design with a small Hundertwasser influence. Early forms expected a tree number; the Hundertwasserhaus example was a location shortcut. Address, species and tag search gained separate handling, then one input with suggestions. Browser geolocation, a clickable map, TanStack Router, TanStack Query, and mouse-wheel/trackpad zoom followed. The app was tested against Vienna’s real service and deployed to Pages. The wider city-maintained register and the records actually exposed by the open feed have different coverage. Preserve that distinction when quoting Vienna’s tree totals. [Vienna README and live app](https://github.com/dvkam/baumkataster-wien#readme)

The first public implementation used React 19.3.1, TypeScript 7.0.2 and Vite 8.3.5 at the recorded checkpoint. Reproduce builds from each repository's lockfile. The Vienna import began at `c083690`; `0695e8a` added place searches and design work, `1d8992c` unified the input and `c34e0c3` enabled wheel zoom. The atlas is a separate public repository so experiments can proceed independently of Vienna.

**26–27 October.** The initial Tree Atlas pilot used 11,388 records from bounded study areas in Vienna, Geneva and Porto with an optional Copernicus overlay. Three acceptance interfaces were agreed: source import, published catalogue, and user journeys. The first full inventories contained 233,102 Vienna records, 240,827 in Geneva canton and 71,634 in Porto (545,563 combined). Amsterdam, Hamburg and Zürich brought the total to 1,183,099. London, Camden, Edinburgh and Belfast followed. Nottingham stayed out. London excludes the GLA contributor labelled LB Camden, and Camden’s council inventory is published separately. Equal locations and repeated tree facts can be valid. Keep them until an explicit source identity rule says otherwise.

At `8fb09014` the catalogue reached 44 inventories and 7,613,581 source records. The source register lists the acquired files, APIs, fields, reuse terms and gaps. Source geography includes national heritage and cantonal collections alongside cities. Street Tree Layer 2021 polygons show satellite-derived vegetation in selected European urban areas. They have no species or municipal ID. [Source register](../../../docs/source-apis/index.md) · [Canopy layer](../../../docs/copernicus.md) · [Public architecture](../../../docs/architecture.md)

## How the public build works

A source adapter consumes the publisher’s export or paginated API and prepares a validated, immutable release. Files, IDs, units, source notes, attribution and checksums belong to that release. Separate code supports WFS, ArcGIS, tabular downloads, municipal REST interfaces and other source formats. The first browser request reads the catalogue. An early spatial index provides a map before the complete inventory is in memory. Searchable text and exact coordinates have separate readiness states. A worker searches and clusters the data. Full details are fetched by release and ID when needed. TanStack Router keeps city, filters, area, selection and release in the URL. TanStack Query manages loads and errors.

Hash and count checks detect a truncated download. They cannot tell whether the municipality surveyed a private garden or used the right unit on a particular row. Leave missing coordinates null and keep that row in city-wide search. An explicit area filter can exclude it. Keep map viewport, filter scope, page, selected tree and release separate. Treat failure, pending data and a completed empty search as different states. Keep old links on their original release. [Release operations](../../../docs/operations.md)

London once took about 49 s to make all records searchable in a shaped mobile test. Splitting the complete text index (2.78 MB compressed) from exact geometry (13.03 MB) brought this to 11.71 s. First usable map was 1.57 s; exact map filtering was 47.06 s. The test was a city switch on an emulated phone with blocked external imagery, 4× page CPU slowdown and per-response transfer shaping. Worker CPU and the total network link were not constrained in the same way as a physical phone. [Measurements and procedure](../../../docs/search-performance.md)

## Why there is a backend pilot

The public site’s cost for large inventories fell on each visitor: downloads, decoding, memory, searching and building the spatial index. A service can answer a complete query without putting the full inventory on the phone. A forwarding wrapper would pass municipal outages, paging limits and unversioned changes through to visitors. The chosen architecture imports APIs and spreadsheets through the same owned release pipeline, queries local validated data and keeps frozen release links reproducible. A monthly acquisition cycle was proposed. The current process is manual. If a source changes, stage a new release, reconcile additions/changes/disappearances, then promote the validated catalogue pointer. Keep the former snapshot available for old links. PostgreSQL is the data store. Git holds source, manifests, licensed public artifacts and reproducible checks.

The pilot covers London, Vienna, Geneva and Porto, with full online search plus downloaded complete city search/map filtering. Offline full details require an explicit save. Basemap tiles and the Copernicus WMS are separate network services. A complete first online search should finish within three seconds, including a sleeping backend waking up. Both modes must retain exact membership and ordering.

**Language and hosting decision, 2 November.** Performance, reliability and the chance to learn a language received equal weight. C and C++ offer mature native libraries with lifetime and concurrency obligations. Rust was a credible systems choice; Java a mature service choice with JVM cost to measure. OCaml offered strong domain modelling; Smalltalk/Pharo offered interactive development with image deployment to qualify. Zig offered allocation control with a changing toolchain. Assembly offered no measured advantage for this workload. Carbon was selected as a local feasibility experiment because its C++ interoperability could reuse proven libraries. “KakaoTalk” in the early discussion meant Smalltalk. The resulting service includes substantial C++ and SQL. A production language decision still depends on measured operation and maintainability.

The cost study compared €10, €30 and €60 monthly envelopes, a maintained home server, self-managed EU VPS options and managed database plus service offerings. The selected plan was self-hosting within €30/month including applicable tax: €20 server/IP/provider backup, €4 independent backups, €1 amortized hostname and €5 contingency. These figures are allocations from the plan. Recheck current acquisition cost, power, traffic, tax, backup and stock when choosing hardware or a provider. No hosting was bought.

## Carbon to database, in order

1. The first WSL experiment proved compilation, local HTTP/JSON and a PostgreSQL round trip. Ubuntu 24.04 hosted PostgreSQL 16.15 directly. Carbon selects routes and maps requests and errors; libmicrohttpd, json-c, libpq and the C++ bridge handle transport, JSON and pooled connections. The service binds to loopback.
2. A stalled synchronous cancellation held a 200 ms request for about 1,205 ms. The isolated libpq 17.11 nonblocking cancellation path completed the same fault in about 351 ms. Cancelled sessions are retired so a late cancel cannot affect the next borrower. Disconnect handling, write-half-close behavior, absolute request-phase limits, single-use attempt IDs, queue bounds and concurrency tests followed. A TLS 1.3 cancellation fault and rejection of an untrusted certificate were tested at the transport PoC stage. A browser-facing hosted HTTPS service and a full recovery/overload trial on hardware remain open. [HTTP PoC](../tree-atlas-carbon-poc/SERVICE.md)
3. The v1 contract pins all four snapshots and independent reference results. Identity includes dataset, release and exact source ID. Preserve leading zeros, composite tags and release ordinal. Use Unicode 17 NFD, remove diacritics, apply locale-independent root lowercase and ECMAScript end trimming. Text matches literal substrings, including percent and underscore. Enforce exact counts, bounded viewport markers and access to all cluster members. The reference oracle does not call the application search engine. [Frozen contract](../tree-atlas-contract-v1/CONTRACT.md)
4. A restricted staging loader imported London (1,111,784), Vienna (233,102), Geneva (240,827) and Porto (71,634). The transaction moves from loading to staged to validated; the API reader cannot publish or edit source rows. Independent checks reconciled canonical IDs, fields, order, positions and hashes for **1,657,347 records**. All rows in these four snapshots happen to have positions. Unlocated cases also need fixtures and wider public catalogue tests. [Database setup and roles](../tree-atlas-postgres-pilot/README.md)
5. The inventory adapter added complete search, exact totals, paging, viewport aggregation, cluster members, details and suggestions. Cache keys bind requests to their release and filters. Cancelling one request must preserve other borrowers. The frontend validates response identity and keeps API and offline sessions separate. Saving a city writes verified complete search and geometry assets atomically. An unsaved detail while offline remains an explicit unavailable state. [API](../tree-atlas-carbon-inventory-api/README.md) · [Offline frontend](../tree-atlas-local/README.md)

## Run a local checkout

For the public app, follow the [root README](../../../README.md). Install the pinned dependencies, run the project checks and build before running the browser journeys against preview. Most UI tests block external map imagery so failures in the city inventory stay distinguishable from tile failures.

For the database pilot, start at [the workspace guide](../README.md). In WSL, from the repo root, prepare its ignored link to licensed input with `python3 experiments/local-pilot/scripts/prepare-workspace.py`. Follow the [clean setup](../CLEAN-ROOM.md) or the existing-toolchain procedure in the workspace guide. Create the restricted roles, import the pins and run the independent readback before starting the API. Install the SQL functions and build the adapter with the commands in the [API guide](../tree-atlas-carbon-inventory-api/README.md). Use the current lockfiles and checksum pins. Do not copy another developer's configuration.

From `experiments/local-pilot/tree-atlas-local`, run `python3 scripts/run-local.py` to start the local production frontend and read-only API. The launcher reports the local URL. Choose London, search Acer, pan without applying an area, select a cluster and inspect its member list. Download a city, explicitly save one record's details, disconnect, reload and repeat the search. A second unsaved detail should explain its offline availability. Stop the launcher after use. The [CI workflow](../../../.github/workflows/verify-local-pilot.yml) documents the repeatable PR subset. The [validation guide](../BRANCH-VALIDATION.md) distinguishes it from full enumeration and isolated restore.

The repository contains code, locked inputs, attribution, validated licensed public assets and repeatable tests. Database storage, dumps, local role files, raw downloads, SSH material, access tokens, compiled runtimes, dependencies, caches, browser profiles and private scan evidence belong outside source control. Source code publication does not provide a public API origin. Preserve the draft and test gates before considering a merge.

## Hardware and open product decisions

The suggested experimental floor was Pi 4 or 5, 4 GB RAM, a 64-bit OS and an SSD with at least 32 GB free. The roomier option was Pi 5 with 8 GB. These are planning figures. No Pi measurement established them. A possible Pi 3 requires actual model, RAM, CPU architecture and storage verification. The current known working Carbon toolchain is x86-64. Qualify ARM64 or select another compatible host before claiming Pi support. Check the recovery copy off-device, PostgreSQL network isolation, service privileges, TLS, patching, disk headroom and requests under load. A second machine or fresh VM is still necessary for an independent recovery drill. [Hosting and storage notes](../PUBLISHING-AND-HOSTING.md)

Open decisions include API origin and release retention, self-management versus managed service, recovery objectives, full offline street-basemap rights/storage, hardware budget, and whether measured spatial workloads justify PostGIS. Keep the two public apps operational while the pilot earns those decisions.
